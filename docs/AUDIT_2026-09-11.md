What an indexer can rebuild per swap from these events alone:
- **PoolId, fee amount, fee currency:** yes.
- **What the trader paid and received:** yes, but only for swaps that emit.
  - `amount0`/`amount1` are the swap amounts before the fee. The hook receives them before `Hooks.sol:312` subtracts its fee.
  - So the net is that amount minus `feeAmount` on the fee currency.
- **Trader: missing.**
  - `_afterSwap(address, …)` throws away its first argument (:263).
  - That argument is the swap router anyway, not the trader (`Hooks.sol:300`).
- **Swaps with a zero fee: missing entirely.** The hook returns before emitting when the fee rounds to 0 (:277), which is any swap under 100 raw units on the fee side.

This contradicts `CLAUDE.md:5520` and the hook's own comment at :104-106. Both say everything is derivable from our logs alone.

**2. Constructor validation.** **VERIFIED**
- `BallistaFeeHook is BaseHook` (:50), imported from `@uniswap/v4-periphery/src/utils/BaseHook.sol` (:7). Installed versions: v4-periphery 1.0.3 and v4-core 1.0.2.

- The production hook does not override that check. Only the test mock does (`contracts/mocks/BallistaFeeHookTestable.sol:31`), and the deploy script deploys the real hook (`deploy-v4-stack.js:164`).
- **So "a mis-mined salt fails silently" is false.** The CREATE2 deploy reverts and the script aborts (:233-236). The hook's own comment says exactly this (:170-177).
- Where the false claim is made:
  - `CLAUDE.md:4795-4797`: "A missing flag does not revert — the callback is simply never invoked."
  - `CLAUDE.md:4850-4853`: "Nothing reverts and nothing logs." The same section then describes the BaseHook check at :4858-4862, so §20.9 contradicts itself.
  - `CLAUDE.md:5395-5397`: "The failure is silent."

- The runbook (:60-64) also gets the mechanism wrong:
  - A stray transaction changes the deployer's nonce, but the hook's CREATE2 address does not depend on that nonce (`mine-hook-salt.js:123-126`).
  - What it breaks is the predicted adapter and LFX1 addresses.
  - `requireNonce` (`deploy-v4-stack.js:306-315`) and the adapter's binding check (`BallistaV4Adapter.sol:174-175`) catch that loudly.

**3. Permissions.** **VERIFIED**
- `getHookPermissions` (:178-195) sets exactly three flags true: `beforeInitialize` (:180), `afterSwap` (:187) and `afterSwapReturnDelta` (:191). The other eleven are false.
- The flag values are `1<<13`, `1<<6` and `1<<2` (`Hooks.sol:29`, :39, :45). ORed together locally they give `0x2044`.
- Nothing else can be set:
  - BaseHook enforces all 14 bits.
  - The adapter requires exactly `REQUIRED_HOOK_FLAGS` (`BallistaV4Adapter.sol:85-86`, :156-157).
  - The deploy script requires the exact set (:178-180).

**4. Fee custody.** **VERIFIED**
- The hook takes real tokens with `poolManager.take(feeCurrency, address(this), fee)` (:326).
  - `take` transfers the currency out of PoolManager (`PoolManager.sol:291-296`).
  - There are no ERC-6909 mints anywhere in the hook.
- Payout is `claim()` (:382-388) and `claimToken()` (:390-396): a plain `safeTransfer` from the hook's own balance, with no `unlock`.
- A sweep does exist: `sweep(PoolId)` (:349-378). It is permissionless and moves accrued fees into per-recipient balances without transferring anything.

**5. Transfers in the swap path.** **VERIFIED** in code; the blocklist behaviour is **INFERRED** (from CLAUDE.md §2).
- The only token movement in the swap path is PoolManager paying the hook itself (:326). Nothing in a swap pays the creator or the protocol.
- So a blocklisted creator or protocol recipient cannot make swaps revert. Only their own `claim()` fails (:386).
- One exception: if the **hook's own address** were blocklisted, the USDC transfer into it would revert. So would every swap whose fee is taken in USDC: exact-in sells and exact-out buys (:300-304).

**6. Recipients.** **VERIFIED**
- The creator comes from `lfx1.curves(token)` (:236) and is stored as `feeRecipient` (:246).
  - This happens once, inside `_beforeInitialize`.
  - That runs when the adapter initialises the pool at graduation (`BallistaV4Adapter.sol:383`, reached from `LFX1.sol:656`).
- The protocol recipient is a constructor argument (:157), stored as `immutable` (:73) and checked for zero (:161).
- `deploy-v4-stack.js` passes the same `--treasury` value (:111) to both places:
  - the hook's protocol recipient (:166);

- The runbook leaves that value to the operator (:137).
- LFX1's treasury can be changed later with no event (`LFX1.sol:828-831`), but the hook's recipient cannot. The two can silently drift apart.

## B. LFX1: router, recovery, config

**7. Router activation.** **VERIFIED**
- The constructor (`LFX1.sol:211-221`) does: `if (initialRouter_ != address(0)) { emit RouterProposed(...); router = initialRouter_; emit RouterActivated(...); }`.
- It does not check code length and makes no calls into the router.

**8. Router switching.** **VERIFIED** (`proposeRouter` :742-746, `activateRouter` :748-756, `revokeRouter` :758-764)
- **Timelock:** 24 hours (`ROUTER_TIMELOCK`, :29).
- **Restrictions on the new address:** only that it is non-zero (:743). No code or interface check.
- **Switching back to an earlier router:** allowed. It needs a fresh proposal and another 24 h, because activation consumes the proposal (:753).
- **Re-pointing more than once:** no limit. Proposals are stored per address (:31), and re-proposing restarts the clock (:744).

**9. Router at graduation.** **VERIFIED**
- `_performGraduation` reads the factory's current `router` at call time (:646, :653-656).
- Pinned per token at creation: the LP recipient (snapshot at :359, used at :663), the threshold and the fees. Not the router.

**10. Recovery.** The mechanism is **VERIFIED**; the outcome is **INFERRED** (never executed).
- **(a) Switch to v2.** `proposeRouter` → 24 h → `activateRouter`. Then anyone can call `graduate(token)` (:690-696), which uses the new router (:656). Whether v2 then succeeds depends on Q30.
- **(b) New adapter and hook bound to the existing LFX1.** Nothing prevents it.
  - The adapter's constructor checks only a non-zero `lfx1`, a non-zero hook, the flags, and that the hook names this adapter (`BallistaV4Adapter.sol:121-182`).
  - The hook's constructor checks only for zero arguments (`BallistaFeeHook.sol:153-168`).
  - Neither reads LFX1's router or any registry.
  - A new hook means a new pool, so nothing collides with the old stack.
- Both routes need the owner key and at least 24 h. During that time, holders of parked tokens cannot buy or sell (`LFX1.sol:509`, :560).
- **So "the hook can permanently brick" is true only for pools that already graduated through it.**
  - Their pool key names the immutable hook, and the LP went to the burn address (`LFX1.sol:44`, :663; adapter :455).
  - Parked tokens can still be recovered by either route.
